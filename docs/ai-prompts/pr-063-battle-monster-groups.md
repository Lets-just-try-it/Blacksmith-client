## 주요 요청

1. 작업 순서(스폰 지점 → 가까운 무리로 NavMesh 이동 → 시체 → 던전 하루 유지)에 문제가 없는지 엔지니어 관점으로 검토한다.
2. 몬스터 무리 스폰 지점은 모험가 시작 지점과 너무 가깝지 않게, 시작할 때 화면에 보이지 않게 둔다.
3. 모험가는 가장 가까운 무리로 이동해 싸우고, 끝나면 다음으로 가까운 무리로 간다.
4. (중간 피드백) 무리를 만나기 전 이동이 버벅이고 부자연스럽다. 대열은 꼭 지키지 않아도 되니 서로 부딪히지 않고 자연스럽게 걷게 하고, 이동 속도를 2~3배 올린다.
5. (중간 피드백) 걷는 속도를 더 올리고, 이동 애니메이션 속도도 맞춘다.
6. (중간 피드백) 전투 뒤 원거리가 근접보다 앞서 있으면, 원거리는 조금 느리게, 근접은 조금 빠르게 걸어 근접이 앞에 서게 한 뒤 속도를 맞춘다.
7. (중간 피드백) 애니메이터에 속도에 따라 걷기·달리기가 바뀌는 설정이 있는지 확인하고, 없으면 `Hero@Common_Run`을 쓴다. 달리기는 배속 없이 재생한다.

## AI와 논의한 내용

### 작업 순서 검토

지금 전투는 호스트가 결과를 미리 계산하고 참가자가 같은 시드로 재생하는 결정적 구조다. NavMesh로 이동하면 기기마다 경로가 달라 결과를 미리 계산할 수 없다고 짚었다. 그래서 이동을 `Core`의 정수 격자 경로로 계산하자고 제안했다. 화면 범위는 결정적이지 않으므로 "화면 밖" 조건은 시작 지점에서의 거리로 바꾸자고 했다. 하루 유지에서는 시체 위치가 장비에 따라 달라지는 전투 결과에 달려 있으므로, 시뮬레이션을 다시 돌리지 말고 결과를 저장해야 한다고 정리했다. 사용자가 Core 격자 방식을 골랐다.

### 무리 전투 설계

잡몹 무리는 처음부터 스폰 지점에 세우고, 모험가가 시야에 들면 다가오게 했다. 파티는 걸어서 가장 가까운 무리로 8방향 거리장을 따라 걷고, 보스는 잡몹을 모두 토벌하면 나타나게 했다. 무리를 미리 만들어 두면 늦게 들어온 참가자 재생과 풀링 문제가 단순해진다. 웨이브 이름을 무리로 바꿀지 사용자에게 물었고, 함께 바꾸기로 했다.

### 이동 다듬기

처음에는 보이지 않는 기준점 뒤의 대열 자리를 따라가게 했다. 그런데 기준점이 칸마다 꺾여 대열이 통째로 돌아 버벅였다. 그래서 모험가마다 경로를 몇 칸 앞까지 펴서 걷고 서로 비켜 서게 바꿨다. 실제 맵 측정에서 걷기 애니메이션 속도를 이동 속도에 맞춰 올렸는데, 공용 컨트롤러에 이미 `Speed` 블렌드 트리(대기·걷기·달리기)가 있었고 전투만 걷기 하나뿐인 별도 상태를 쓰고 있었다. 공용 컨트롤러는 고치지 않고, 전투에서 `Speed`를 넣어 블렌드 트리를 쓰게 했다.

## 주요 결정

- 이동은 NavMesh 대신 `Core`의 정수 8방향 격자 경로로 계산한다(사용자 결정).
- 기획 7.1의 `[미정]` 보스 등장 자리는 "시작 지점에서 걸어서 가장 먼 곳"으로 정했다(사용자 결정, 기획 문서 갱신).
- 무리 스폰은 시작 지점·다른 무리·가장자리에서 떨어지게 두고, 거리는 `[추정]` 수치로 데이터에 둔다(40m / 32m / 4m).
- 웨이브 코드 이름을 무리로 바꾼다(사용자 결정).
- 걸을 때 대열은 지키지 않고, 서로 비켜 서며, 원거리가 앞서면 25% 속도를 바꿔 근접이 앞에 서게 한다(사용자 요청, 비율은 `[추정]`).
- 걷는 속도는 초당 8m(`_marchSpeed` 40)이고, 달리기 동작은 배속 없이 재생한다(사용자 결정).
- 보상·경험치는 데이터 순서가 아니라 토벌 순서로 계산한다.
