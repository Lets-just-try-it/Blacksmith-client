# PR #54: docs: 문서 간소화와 절 단위 읽기 안내 추가

## 개요

- 브랜치: `docs/slim-docs`
- 대상 브랜치: `dev`
- PR: #54
- 작성일: 2026-11-11
- 담당 영역: 시스템·데이터
- 작업 목적: 작업할 때마다 읽는 공통 문서의 양을 줄여, 필요한 부분만 빠르게 찾아 읽게 한다.

## 주요 요청

1. 공통 md 문서가 너무 길고 복잡하다. 주로 AI 에이전트가 읽는 문서인데, 작업마다 읽느라 토큰을 많이 쓴다. 간소화 계획을 먼저 제시한다.
2. 여러 영역에 걸친 기능(예: 전투에서 몬스터 무리가 죽은 자리를 채집에서 그대로 갈무리)이 있는데, 기획 문서를 영역별로 나눠도 문제가 없는지 검토한다.
3. 기획 문서는 한 파일로 유지하고 간소화를 진행한다.

## AI와 논의한 내용

### 문서별 크기와 읽는 빈도

- `PROJECT_PROGRESS.md`(93KB): 대부분이 구현 설명과 확인 기록이었다. 코드와 PR, AI 협업 기록에 이미 있는 내용이다.
- `GAME_CONCEPT.md`(90KB): 어떤 작업을 하든 처음부터 끝까지 읽혔다.
- `CLAUDE.md`(16KB): 대화마다 자동으로 읽힌다.

### 기획 문서를 영역별로 나눌지

영역별 파일로 나누는 안을 검토했다. 몬스터 시체 갈무리 하나만 봐도 5.1, 7.1, 7.2, 7.4절에 걸쳐 있었다. 나누면 여러 파일을 함께 읽어야 하고, 같은 내용을 여러 곳에 적다가 서로 어긋날 수 있다.

그래서 한 파일로 두고 다음 방식을 쓰기로 했다.

- 필요한 절만 읽는다.
- 여러 영역이 쓰는 내용은 한 절에만 적고, 다른 곳은 절 번호로 참조한다.
- 맨 위에 영역 연결표를 둔다.

## 주요 결정

- 사용자 결정: 기획 문서는 영역별로 나누지 않고 한 파일로 유지한다.
- 사용자 결정: 코드 주석의 잘못된 기획 절 번호(협동 멀티 8절 → 9절)를 함께 고친다.
- 사용자 결정: 기획 PR(#53)을 먼저 병합하고, 이 PR을 따로 올린다.
- 정리하면서 정한 것:
  - 진행 현황에는 시스템별 상태, 핵심 진입점, 확인하지 않은 것, 남은 작업만 적는다.
  - 구현 방법과 확인 기록은 PR 본문과 AI 협업 기록에 적는다.
  - 개발 환경 설정은 `docs/SETUP.md`로 분리한다.
  - 기획 문서의 절 번호는 바꾸지 않는다. 코드 주석이 참조한다.
  - 확정된 팀 논의 항목은 15절 표에서 빼고, 남은 번호는 다시 매기지 않는다.

## 검증 내용

- 크기:
  - `PROJECT_PROGRESS.md`: 93KB → 12KB (`SETUP.md` 3KB를 따로 둠)
  - `GAME_CONCEPT.md`: 90KB → 75KB
  - `CLAUDE.md`: 16KB → 11KB
- `GAME_CONCEPT.md`:
  - 절 제목과 번호가 바뀌지 않았다.
  - 기획 표시([미정], [추정], [담당자 결정], [고도화])는 고치기 전과 같은 123개다.
- `PROJECT_PROGRESS.md`에 새로 적은 클래스·데이터 이름이 실제 코드에 있는지 확인했다. 틀린 이름 하나는 `AdventurerLevelRules`로 바로잡았다.
- 다른 문서가 가리키는 `CLAUDE.md` 절 제목("기획 문서", "네트워크 구조" 등)이 모두 남아 있다.
- 문서와 주석만 바꿨으므로 빌드와 테스트는 하지 않았다.

## AI 활용 범위

- AI가 한 일:
  - 문서 크기를 쟀다.
  - 간소화 계획과 영역별 분할의 문제점을 정리했다.
  - 세 문서를 다시 쓰고 줄였다.
  - 이름과 참조를 확인했다.
- 사용자가 한 일:
  - 문서가 길다는 문제를 제기했다.
  - 영역에 걸친 기능의 문제를 짚었다.
  - 한 파일 유지, 주석 수정, PR 순서를 정했다.
  - 커밋 내용을 검토하고 승인했다.
