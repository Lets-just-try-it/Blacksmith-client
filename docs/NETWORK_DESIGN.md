# 멀티플레이 네트워크 설계

> 표기: **[미정]** 아직 정하지 않았다 / **[추정]** 예정된 방향이며 바뀔 수 있다

## 1. 설계 목표와 원칙

이 게임은 친구끼리 즐기는 소규모 협동 게임을 전제로 한다. 치팅 방지를 위한 복잡한 검증보다 플레이 경험과 게임 상태의 정합성을 우선한다.

- 네트워크 모드: Photon Fusion 2 Host 모드
- 이동 반응성: 클라이언트 예측(Client-side Prediction)을 적용한다.
- 공유 상태 관리: 여러 플레이어가 공유하는 게임 상태는 호스트가 관리한다.
- 미니게임 판정: 미니게임을 실행하는 클라이언트가 정확도를 계산하고, 호스트는 전달받은 결과를 신뢰한다.
- 치팅 방지: 별도의 복잡한 치팅 방지와 서버 측 판정 로직은 구현하지 않는다.

## 2. 기능별 처리 주체

| 기능 | 처리 주체 | 처리 방식 |
| --- | --- | --- |
| 캐릭터 이동 | 클라이언트, 호스트 | 클라이언트 예측과 호스트 권한 기반 상태 동기화 |
| 작업대 사용 요청 | 클라이언트 → 호스트 | 작업대 사용 요청 전송 |
| 작업대 사용권 관리 | 호스트 | 먼저 처리된 유효한 요청에 사용권 부여 |
| 미니게임 실행 | 사용자 클라이언트 | 노트 표시, 입력 처리, 정확도 계산 |
| 미니게임 결과 전달 | 클라이언트 → 호스트 | 정확도 결과 전송 |
| 미니게임 결과 반영 | 호스트 | 전달받은 결과에 따라 게임 상태 갱신 |
| 작업대 상태 동기화 | 호스트 | 작업대 사용 상태를 모든 클라이언트에 동기화 |
| NPC 대화 점유 | 호스트 | 먼저 처리된 대화 요청에 대화 상대 지정, 선택 결과를 같은 조건으로 다시 확인한 뒤 반영 |
| 대화 진행 | 각 클라이언트 | 대사 넘기기, 선택지 강조·확정, 조건 평가 (로컬) |
| 함께 보는 대화 | 호스트 → 모든 클라이언트 | 호스트가 재생 RPC를 보내고, 모두 다 읽으면 함께 닫음 |
| 자동 전투 재생 | 호스트 → 모든 클라이언트 | 호스트가 파견 정보(시드, 던전, 스테이지, 모험가 ID)를 동기화하고, 각자 같은 전투를 재생 |
| 전투 결과 반영 | 호스트 | 시작할 때 계산해 둔 결과를 전투 씬을 내리기 직전에 반영 |

## 3. 플레이어 입력 처리

플레이어 입력은 Fusion의 `NetworkInput`으로 틱마다 호스트에 전달한다. 입력 장치를 읽는 쪽과 입력을 사용하는 쪽을 나눈다.

| 구성 요소 | 위치 | 역할 |
| --- | --- | --- |
| `PlayerInputCollector` | `NetworkRunner` 프리팹 | 로컬 입력 장치를 읽어 `PlayerNetworkInput`을 채우고 `input.Set()`으로 넘긴다 |
| `PlayerNetworkInput` | 구조체 (오브젝트에 붙지 않음) | 틱마다 보내는 입력 데이터. 수집기와 기능 클래스 사이의 약속이다 |
| 기능 클래스 (`PlayerMovement` 등) | `Player` 프리팹 | `FixedUpdateNetwork()`에서 `GetInput()`으로 입력을 꺼내 처리한다 |

```text
[러너] PlayerInputCollector.OnInput
    → 입력 장치를 읽어 PlayerNetworkInput 생성 → input.Set(data)
    → Fusion이 틱별 입력으로 저장하고 호스트로 전송
[Player] 기능 클래스.FixedUpdateNetwork
    → GetInput(out PlayerNetworkInput input)으로 꺼내 처리
```

- 수집기를 러너에 두는 이유: `OnInput`은 러너 콜백이고, PC마다 수집할 입력은 하나뿐이며, 러너는 Player가 스폰되기 전부터 존재한다.
- `GetInput()`은 호스트(받은 입력으로 실제 계산)와 입력한 본인 PC(예측)에서만 `true`다. 다른 플레이어의 PC에서는 `false`이고, 그 캐릭터는 호스트가 동기화한 결과만 받아 표시한다.
- 새 입력이 필요하면 `PlayerNetworkInput`(필드나 `PlayerButton` 항목)과 `PlayerInputCollector`(값을 채우는 코드)만 고친다.
- 기능 클래스는 키보드 등 입력 장치를 직접 읽지 않는다. 호스트에는 클라이언트의 입력 장치가 없고, 예측을 위한 재계산도 틀어진다.
- 미니게임 입력은 이 흐름을 쓰지 않는다. 미니게임은 실행하는 클라이언트에서 로컬로 처리하고 결과만 호스트에 보낸다 (5절).

### 3.1 캐릭터 조작 입력 잠금

미니게임, 대화창처럼 하는 동안 캐릭터가 움직이거나 다른 상호작용을 시작하면 안 되는 기능은 `PlayerNetworkInputLock`(`Network/`, 에셋 `03.ScriptableObjects/Runtime/PlayerNetworkInputLock.asset`)으로 캐릭터 조작 입력을 잠근다.

- 하는 일: 잠긴 동안 `PlayerInputCollector`가 틱마다 호스트로 보내는 `PlayerNetworkInput`(이동 방향, 버튼)을 빈 값으로 보낸다. 그래서 캐릭터가 멈추고, 상호작용 버튼으로 시작하는 요청(대화 요청 등)도 나가지 않는다.
- 막지 않는 것: 키 입력과 RPC는 막지 않는다. 입력 액션을 끄지 않으므로 미니게임이 Space·WASD 등 어떤 키를 쓰든 그대로 읽을 수 있고, 미니게임 결과나 대화 선택 같은 RPC도 그대로 보낸다.
- 여러 기능이 동시에 잠글 수 있다. 잠근 쪽마다 따로 기록하므로 한쪽이 풀어도 다른 쪽의 잠금은 남는다. (예: 담금질 중 함께 보는 대화가 열렸다 닫혀도 담금질이 끝날 때까지 잠긴 상태가 유지된다.)

사용 규칙:

1. 에셋을 `[SerializeField] private PlayerNetworkInputLock _inputLock;`으로 인스펙터에서 받는다. 런타임 검색으로 찾지 않는다.
2. 시작할 때 `_inputLock.Lock(this)`, 끝날 때 `_inputLock.Release(this)`를 부른다.
3. 비정상 종료에도 풀리도록 `OnDisable`에서도 `Release(this)`를 부른다. 잠그지 않은 상태에서 불러도 안전하다.
4. 그 기능에 필요한 입력은 켜진 입력 액션을 직접 읽는다. 입력 액션이나 액션 맵을 `Disable()`하지 않는다. 끄면 같은 키를 쓰는 다른 기능이 깨진다.
5. `PlayerInputCollector`에 기능별 잠금 속성을 새로 추가하지 않는다.

- 잠금 중에도 `NetworkInput`으로 무언가를 보내야 하는 기능(예: 미니게임 도중 캐릭터가 실제로 움직여야 하는 경우)이 생기면 이 장치와 충돌한다. 그때 잠글 범위를 나누는 방식으로 확장한다.
- 세션이 시작될 때(`PlayerInputCollector`가 켜질 때) 남은 잠금을 비운다. 에디터에서 도메인 리로드 없이 플레이를 다시 시작하는 경우를 위한 처리다.

## 4. 작업대 사용권 관리

작업대는 한 번에 한 명의 플레이어만 사용할 수 있다. 사용권 부여와 해제는 호스트가 관리한다.

### 4.1 작업대 상태

| 상태 | 의미 |
| --- | --- |
| `Available` | 사용 가능한 상태 |
| `InProgress` | 플레이어가 사용 중인 상태 |

작업대는 다음 정보를 관리한다.

- `State`: 현재 작업대 상태
- `CurrentUser`: 현재 작업대 사용자의 `PlayerRef`
- `SessionId`: 현재 미니게임 세션 식별자. 호스트가 사용권을 줄 때 새로 발급한다.

### 4.2 사용 요청 처리

1. 클라이언트가 호스트에 작업대 사용을 요청한다.
2. 호스트는 작업대가 `Available` 상태인지 확인한다.
3. 사용 가능하면 요청한 플레이어를 `CurrentUser`로 설정하고 새 `SessionId`를 발급한다.
4. 작업대 상태를 `InProgress`로 바꾼다.
5. 호스트가 해당 클라이언트에 사용 승인과 `SessionId`를 전달한다.
6. 클라이언트는 승인받은 뒤 미니게임을 시작한다.

여러 플레이어가 동시에 요청해도 호스트가 먼저 처리한 유효한 요청만 승인한다. 이를 통해 작업대의 동시 사용을 막는다.

## 5. 미니게임 진행과 결과 처리

미니게임의 노트 표시, 입력 처리, 정확도 계산은 미니게임을 실행하는 클라이언트에서 한다. 호스트는 개별 노트의 판정을 검증하지 않는다.

미니게임에는 실패가 없다. 정확도가 0이어도 미니게임은 완료되며, 정확도에 따라 결과 등급만 달라진다.

미니게임이 끝나면 클라이언트는 다음 정보를 호스트에 전달한다.

| 데이터 | 의미 |
| --- | --- |
| `SessionId` | 결과가 속한 미니게임 세션 |
| `Accuracy` | 미니게임 정확도 |

- `Accuracy`는 0~1 실수다.

호스트는 결과를 받으면 다음 순서로 처리한다.

1. 결과를 보낸 플레이어가 현재 작업대 사용자인지 확인한다.
2. 전달된 `SessionId`가 현재 세션과 일치하는지 확인한다.
3. 해당 세션의 결과를 이미 처리했는지 확인한다.
4. 아직 처리하지 않았다면 정확도를 반영해 아이템을 다음 단계 형태로 교체한다.
5. 작업대를 `Available` 상태로 바꾸고 사용권을 해제한다.
6. 변경된 상태를 모든 클라이언트에 동기화한다.

이미 처리한 세션의 결과가 중복으로 도착하면 무시한다. 이는 치팅 방지가 아니라 중복 보상 지급이나 작업대 상태의 중복 변경을 막기 위한 처리다.

정확도를 등급으로 바꾸는 계산은 `Core/`의 순수 C# 함수로 둔다. 아이템 교체 규칙은 `docs/GAME_CONCEPT.md`의 "단계별 아이템 교체"를 따른다.

### 5.1 구현

- 작업대마다 씬 네트워크 오브젝트인 `ForgeStationState`가 `Status`, `CurrentUser`, `SessionId`, `LastProcessedSession`, 사용자가 쓰는 슬롯을 `[Networked]`로 둔다. 사용권을 줄 때 `SessionId`를 1씩 늘려 발급하고, 사용자가 나가면(`IPlayerLeft`) 사용권을 푼다.
- 요청과 결과 RPC는 Player 프리팹의 `ForgePlayerActions`에 둔다. 작업대 화면은 `ForgeChannel` 에셋으로 내 플레이어를 몰라도 요청한다.
  1. 클라이언트: `RpcRequestStart(작업대, 손에 든 슬롯)` (`InputAuthority` → `StateAuthority`)
  2. 호스트: 그 슬롯의 물건이 이 작업대가 받는 재료인지(`CraftingRecipeData.TryFindStep`)와 작업대가 비었는지 확인하고, 사용권을 주면 `RpcStartApproved(작업대, SessionId)`, 아니면 `RpcStartRejected(작업대, 이유)`를 해당 클라이언트에 보낸다.
  3. 클라이언트: 승인을 받으면 미니게임을 시작하고(`ForgeStationLink.Approved`), 끝나면 `RpcSubmitResult(작업대, SessionId, Accuracy)`를 보낸다.
  4. 호스트: `ForgeStationState.TryFinish`가 사용자, 세션, 중복 여부를 확인하고 사용권을 풀면, `Core/Forge/CraftingRules`로 결과물을 만들어 `PlayerInventoryState.TryReplaceOne`으로 바꾼다.
- 호스트가 자기 요청을 보낼 때는 RPC가 바로 실행되어 승인이 요청 호출 안에서 돌아온다. 그래서 요청 쪽(`ForgeStationLink`)은 보내기 전에 기다림 상태로 바꿔 둔다.

## 6. 예외 상황 처리

### 6.1 미니게임 도중 클라이언트 연결이 끊어진 경우

정상적인 게임 진행 중에는 미니게임 도중 나갈 수 없게 한다. 다만 네트워크 문제 등으로 클라이언트 연결이 끊어질 수 있다.

1. 호스트가 해당 플레이어의 연결 종료를 감지한다.
2. 해당 플레이어가 작업대를 사용 중인지 확인한다.
3. 사용 중이라면 작업대 사용권을 해제한다.
4. 작업대를 `Available` 상태로 바꾼다.
5. 변경된 상태를 다른 클라이언트에 동기화한다.

이를 통해 비정상적인 연결 종료로 작업대가 계속 사용 중 상태에 머무는 문제를 막는다. 결과를 반영하지 않았으므로 재료 아이템은 원래 형태로 플레이어 슬롯에 남는다.

### 6.2 미니게임 결과가 중복으로 도착한 경우

이미 결과를 처리한 세션의 결과는 무시한다. `SessionId`로 현재 세션과 일치하는지 확인하고, 세션별 결과 처리 여부를 관리한다.

### 6.3 호스트가 게임을 종료한 경우

호스트가 게임을 종료하면 게임 세션 전체를 종료한다.

- 호스트의 게임 세션을 종료한다.
- 모든 클라이언트의 연결을 종료한다.
- 호스트 이전이나 세션 유지 기능은 구현하지 않는다.

저장은 밤 결과창 뒤에만 하므로, 호스트가 낮 도중 종료하면 그날 낮 진행분은 저장되지 않는다.

### 6.4 재접속한 플레이어 식별

`PlayerRef`는 재접속하면 바뀔 수 있으므로, 개인 인벤토리 같은 플레이어별 상태는 `PlayerRef`가 아닌 별도 식별자로 찾는다.

- [추정] 스토브·스팀 플랫폼 계정 정보로 플레이어를 식별한다. 예정된 방향이며 바뀔 수 있다.

## 7. 대화

대사 표시와 진행(넘기기, 선택지)은 각 PC에서 로컬로 한다. 네트워크가 관여하는 것은 누가 어느 NPC와 대화 중인지, 고른 선택지의 결과, 함께 보는 대화의 시작과 끝뿐이다. 다이얼로그 시스템(`Dialogue/`)은 누가 대화를 열었는지 모르고, 여는 쪽이 `DialogueChannel.Play(DialogueRequest)`로 요청하고 콜백으로 결과를 받는다.

### 7.1 NPC 대화 점유

NPC(`DialogueSeat`)는 한 번에 한 명과만 대화한다. 작업대 사용권(4절)과 같은 방식이다.

| 상태 | 위치 | 의미 |
| --- | --- | --- |
| `DialogueSeat.Talker` | NPC | 대화 중인 플레이어. 점유 판정은 이 값으로만 한다 |
| `DialoguePlayerActions.DialogueTarget` | Player | 대화 중인 NPC. 내 화면의 대화 열기·닫기와 다른 플레이어 화면의 "대화 중" 말풍선에 쓴다 |

두 값은 호스트가 같은 RPC 처리 안에서 함께 바꾼다.

1. 클라이언트가 상호작용 키로 `DialoguePlayerActions`의 RPC를 보내 대화를 요청한다.
2. 호스트는 NPC가 비어 있을 때만 두 값을 설정한다. 이미 대화 중이면 무시한다.
3. 요청한 클라이언트는 `DialogueTarget`이 그 NPC로 바뀐 것을 보고 대화창을 연다. 대화창이 열린 동안 캐릭터 조작 입력을 잠근다 (3.1절).
4. 선택지를 고르면 선택 RPC를 보낸다. 호스트는 요청자가 대화 중인 플레이어인지 확인하고, 화면과 같은 조건 함수로 선택지를 고를 수 있는지 다시 확인한 뒤 NPC의 `IDialogueChoiceHandler`에 넘긴다. 화면을 띄운 뒤 상태가 바뀌었을 수 있기 때문이며 치팅 방지 목적은 아니다.
5. 선택지 없이 끝나거나 닫히면 해제 RPC를 보낸다. 호스트는 두 값을 비운다.

예외:

- 대화 중인 플레이어의 연결이 끊기면 호스트가 NPC 점유를 푼다. 플레이어 오브젝트는 디스폰되므로 말풍선도 사라진다.
- 대화 중인 NPC가 사라지면(예: 영입되어 디스폰) 호스트가 `DialogueTarget`을 비우고, 대화창은 닫힌다.

### 7.2 함께 보는 대화

컷씬, 튜토리얼처럼 모든 참가자가 같은 대사를 보는 대화는 씬의 `SharedDialogue`(호스트 소유)가 연다.

1. 호스트가 `SharedDialogue.Play(대사)`를 부르면, 대사의 `DialogueCatalog` 번호를 RPC로 모두에게 보낸다. ScriptableObject는 RPC로 보낼 수 없어서 번호를 보낸다.
2. 각 PC는 자기 속도로 대사를 넘긴다. 다 읽으면 "다른 참가자를 기다리는 중"을 띄우고 자기 플레이어 오브젝트의 RPC로 호스트에 알린다.
3. 시작할 때 접속해 있던 참가자가 모두 다 읽으면(중간에 나간 참가자는 제외) 호스트가 모두에게 닫기 RPC를 보내고 `Finished` 이벤트를 낸다. 튜토리얼·컷씬은 이 이벤트로 다음 단계로 넘어간다.
4. NPC와 대화하던 참가자는 그 대화가 닫히고(점유 해제) 함께 보는 대화가 열린다. 함께 보는 대화끼리는 겹쳐 열지 않는다.

## 8. 자동 전투

밤에 호스트가 파견을 확정하면 전투 씬을 낮 씬 위에 추가로(Additive) 불러오고, 모든 참가자가 같은 전투를 재생한다. 전투 씬의 `BattleState`(호스트 소유 씬 오브젝트)가 파견 정보를 동기화한다. 결과를 반영하면 전투 씬을 내린다.

1. 호스트가 `BattleState.StartBattle`로 시드, 던전, 스테이지 범위, 파티 모험가 ID를 `[Networked]`에 쓴다. 이때 결과를 미리 계산해 호스트에만 담아 둔다.
2. 각 참가자는 바뀐 파견 정보를 `ChangeDetector`로 받아, 모험가 ID로 모험가 정보를 찾아 같은 `BattleSetup`을 만들고 재생한다. 시드와 입력이 같으므로 결과도 같다. 결과창도 각자 띄운다.
3. 결과창의 다음 진행은 호스트만 한다. 호스트가 `BattleState.ConfirmResult`를 부르면 던전 진행 상황을 갱신하고 `ResultConfirmed` 이벤트로 결과와 보상을 넘긴다. 실제 흐름에서는 이 직후 전투 씬을 내리고 다음 날로 넘어간다.
- 씬을 통째로 바꾸지 않고 Additive로 불러온다. 낮 씬이 남아 있어 관리 목록 같은 상태가 사라지지 않고, 매일 낮 씬을 다시 불러오지 않아도 된다.
- 두 씬이 함께 떠 있으면 카메라, Screen Space UI, 실시간 조명이 서로 겹친다. 전투 씬이 떠 있는 동안 낮 씬의 카메라·UI·라이트를 끄고, 전투 씬을 활성 씬으로 둔다. 전투 공간은 낮 씬과 겹치지 않는 좌표에 둔다. EventSystem과 AudioListener는 낮 씬 것만 쓴다.
- 결과는 전투 씬을 내리기 직전에 반영한다. 재생이 끝나는 시점은 참가자마다 다르므로, 먼저 반영하면 아직 재생 중인 참가자의 결과창(레벨업 표시 등)이 바뀐 관리 목록을 기준으로 계산된다.
- 파티는 모험가 ID만 보내고, 각자 낮 씬의 관리 목록에서 찾는다. 전투 씬이 떠 있는 동안에는 관리 목록을 바꾸는 낮 씬 상호작용(영입, 장비 교체 등)을 잠가, 재생하는 동안 모험가 정보가 바뀌지 않게 한다.
- 낮 씬 화면 끄기와 상호작용 잠금은 낮·밤 사이클(대장간 담당)과 광장이 맡는다. 파견 창에서 `BattleState`로 파견 정보를 넘기는 방법과 전투 씬을 불러오고 내리는 코드는 전투가 맡는다.
- [미정] 게임을 껐다 켤 때 이어지는 상태(관리 목록, 던전 진행 상황, 골드 등)의 저장 구조. 지금은 `BattleState`가 테스트 파티 조회와 던전 진행 상황을 임시로 맡는다.

## 9. 인벤토리

인벤토리 칸은 호스트가 소유한 `NetworkInventory`(공용 창고는 씬의 `SharedInventoryState`, 플레이어 슬롯 8칸은 Player 프리팹의 `PlayerInventoryState`)의 `[Networked]` 배열에 둔다. 칸 규칙(넣기, 쌓기, 줄 늘리기, 옮기기)은 `Core/Inventory`의 `InventoryGrid`에 두고, 호스트가 값을 바꿀 때마다 네트워크 값을 격자로 옮겨 규칙을 적용한 뒤 다시 써 넣는다.

1. 창을 여는 일은 각 PC가 로컬로 한다. 공용 창고는 여러 명이 동시에 열 수 있으므로 점유를 두지 않는다. 창을 연 동안에는 `PlayerNetworkInputLock`으로 캐릭터 조작 입력을 잠근다.
2. 칸을 끌어다 놓으면 Player 프리팹의 `InventoryPlayerActions`가 `RpcMoveItem(출발 인벤토리, 출발 칸, 도착 인벤토리, 도착 칸, 출발 칸에 보이던 물건)`을 호스트에 보낸다. 같은 인벤토리 안의 이동과 서로 다른 인벤토리 사이의 이동(공용 창고 ↔ 플레이어 슬롯)을 같은 RPC로 처리한다.
3. 호스트는 출발 칸의 물건이 요청에 담긴 물건과 같은지만 확인하고 옮긴다. 다르면 요청이 도착하기 전에 다른 참가자가 먼저 옮긴 것이므로 무시한다.
4. 바뀐 칸은 각 PC가 `ChangeDetector`로 받아 화면을 다시 그린다. 화면은 요청을 보낸 뒤 결과를 미리 그리지 않는다.

- 제작 결과, 전투 보상, 파견 창은 상자가 아니라 `SharedInventoryState`를 직접 참조해 호스트에서 `TryAdd`, `TryRemove`, `FindSlots`를 부른다.
- `[Networked]` 배열 크기는 컴파일할 때 정해야 하므로, 공용 창고는 최대 크기(가로 5칸 × 40줄, 200칸)를, 플레이어 슬롯은 8칸을 상수로 둔다.
- 플레이어 슬롯은 플레이어 오브젝트에 있으므로 연결이 끊기면 함께 사라진다. 재접속한 플레이어에게 슬롯을 이어 주는 일은 6.4절의 플레이어 식별 방식이 정해진 뒤 추가한다.

## 10. 전체 처리 흐름

### 10.1 캐릭터 이동

```text
플레이어 입력
    ↓
클라이언트 예측으로 즉각적인 이동 반응
    ↓
호스트 권한 기반 상태 처리
    ↓
네트워크 상태 동기화와 필요 시 보정
```

### 10.2 작업대와 미니게임

```text
클라이언트가 작업대 사용 요청
    ↓
호스트가 작업대 사용 가능 여부 확인
    ↓
사용권 부여, SessionId 발급, 작업대 상태 변경
    ↓
사용 승인 전달
    ↓
사용자 클라이언트에서 미니게임 실행
    ↓
클라이언트가 정확도 계산
    ↓
클라이언트가 결과(SessionId, Accuracy) 전달
    ↓
호스트가 사용자·세션·중복 여부 확인
    ↓
결과 반영(아이템 교체)과 작업대 사용권 해제
    ↓
모든 클라이언트에 변경 상태 동기화
```

### 10.3 예외 처리

```text
클라이언트 연결 종료 → 사용 중인 작업대의 사용권 해제, 대화 중인 NPC 점유 해제
중복 결과 수신       → 이미 처리된 세션의 결과 무시
호스트 종료          → 전체 게임 세션 종료
```

## 11. 설계 요약

- 이동 반응성: 클라이언트 예측으로 입력에 즉각 반응한다.
- 공유 상태의 정합성: 작업대 사용권, NPC 대화 점유와 게임 상태는 호스트가 관리한다.
- 캐릭터 조작 잠금: 미니게임·대화 중에는 `PlayerNetworkInputLock`으로 호스트에 가는 이동·버튼 입력만 잠그고, 키 입력과 RPC는 막지 않는다.
- 간결한 미니게임 처리: 정확도 계산은 클라이언트에서 하고, 호스트는 결과를 신뢰한다.
- 중복 처리 방지: 세션 식별자와 처리 여부를 확인해 결과의 중복 반영을 막는다.
- 최소한의 예외 처리: 클라이언트 연결이 끊기면 작업대를 해제하고, 호스트가 종료하면 전체 세션을 종료한다.

호스트는 공유 상태와 결과 반영을 맡고, 클라이언트는 이동 예측과 미니게임 실행을 맡는다.
